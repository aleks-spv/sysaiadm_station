# Плагины SysAiAdm Station

Плагин SysAiAdm Station — отдельный пакет в `plugins/<id>/`, который расширяет приложение: сервер (API и фоновые задачи) и страница в интерфейсе. Ядро приложения про плагин знает только строку регистрации. Это не плагины opencode: те подключаются в «Настройки → Конфиг opencode».

```
plugins/<id>/
  package.json   свой workspace-пакет (@sysadm-plugins/<id>) со своими зависимостями
  server/        экспорт ServerPlugin
  web/           страница — React-компонент без props
```

## Сервер

`plugins/<id>/server/index.ts` экспортирует `ServerPlugin`. Из приложения импортируются только типы `apps/server/src/plugins/types.ts`; всё остальное плагин получает через `ctx`:

```ts
import { Hono } from "hono";
import type { ServerPlugin } from "../../../apps/server/src/plugins/types";

export const examplePlugin: ServerPlugin = {
  id: "example",
  name: "Пример",
  description: "Что делает плагин",
  // Вызывается один раз при старте. Маршруты монтируются в /api/plugins/example.
  routes(ctx) {
    ctx.migrate([`CREATE TABLE example_items (id TEXT PRIMARY KEY, value TEXT NOT NULL)`]);
    return new Hono().get("/items", (c) => c.json(ctx.db.query("SELECT * FROM example_items").all()));
  },
  // Фоновая работа, пока плагин включён. Возвращает функцию остановки.
  start(ctx) {
    const timer = setInterval(() => ctx.log("debug", "tick"), 60_000);
    return () => clearInterval(timer);
  },
};
```

Регистрация: строка в `apps/server/src/plugins/index.ts` (массив `PLUGINS`).

Что даёт `ctx`:

- `db` — общая SQLite. Свои таблицы называйте с префиксом id плагина и создавайте только через `ctx.migrate([...])`: список миграций только дописывается, версия хранится в `settings` под ключом `plugin_schema:<id>`.
- `encrypt(text, aad)` / `decrypt(sealed, aad)` — хранилище секретов (AES-256-GCM мастер-ключом приложения; aad получает префикс id плагина). Сам мастер-ключ плагину не выдаётся.
- `dataDir` — личный каталог плагина, `<DATA_DIR>/plugins/<id>` (в Docker `/data/plugins/<id>`, переживает рестарт).
- `log(level, msg)`, `audit(actor, action, detail, { nodeId, taskId })`; actor берите из `c.get("actor")`.
- `nodes.get(id)` / `nodes.list()` — инвентарь (только чтение).
- `tasks.create({ nodeId, title, prompt, agent?, model?, autopilot? }, actor)` — запустить задачу агенту тем же путём, что и интерфейс; `tasks.get(id)` — её статус.
- `ssh.openShell(nodeId, cols, rows)` — интерактивный PTY на узле по его маршруту через бастионы, с пиннингом ключей; креды плагину не выдаются.
- `upgradeWebSocket` — WebSocket-маршруты (`hono/bun`).

Хук `filterOutput(ctx, { nodeId, taskId, command, shell, exitCode, stdout, stderr })` переписывает вывод `remote_exec` до того, как его прочитает модель (вернуть `{ stdout, stderr, note? }` или `null`). Включённые плагины применяются по порядку `PLUGINS`, ошибка фильтра логируется и пропускается. Если модель вызвала `remote_exec` с `raw: true`, фильтры не применяются. Аудит и статус задачи видят исходный вывод.

Хук `maskOutput(ctx, output)` с тем же ответом прячет секреты. Он идёт после `filterOutput` и применяется и при `raw: true`. Если он бросает ошибку, модель получает пустой вывод с пометкой, а не исходный текст.

Доступ: маршруты плагинов открыты только сессии администратора (cookie). API-токены получают 403. Выключенный плагин отвечает 404, его `start` не вызывается.

## Интерфейс

`plugins/<id>/web/` — интерфейс. Компоненты и API приложения доступны через алиас `@/` (`@/api`, `@/components/ui/button`), Tailwind сканирует `plugins/` автоматически. Каждый импортируемый пакет (react, react-router, `@sysadm/shared`, …) объявите в `plugins/<id>/package.json`: установка изолированная, чужие зависимости не видны. Регистрация в `apps/web/src/plugins/index.ts`:

```ts
{
  id: "example", title: "Пример", icon: Puzzle,
  Page: ExamplePage,                                   // своя страница /plugins/<id> и пункт в левой панели
  nodeActions: [{ id, label, icon, kinds, Dialog }],   // пункт в меню правого клика по узлу, Dialog({ node, onClose })
  panelTools: [{ id, title, icon, kinds, Panel }],     // значок в шапке правой панели, Panel({ node, active })
}
```

Всё необязательно. Панель инструмента не размонтируется, пока открыт тот же узел. Запросы к своему API: `api.plugin<T>("example", "GET", "/items")`.

## Экономия токенов (`plugins/rtk`)

Сжимает вывод команд перед моделью через `filterOutput`. Для `find`/`fd`, рекурсивного `grep`/`rg` и `git diff`/`git show` (одна команда или последнее звено пайпа) вывод проходит через `rtk pipe --filter …` ([rtk](https://github.com/rtk-ai/rtk), Apache-2.0 сборка `rtk-oss`, в образе версия зафиксирована вместе с sha256). Потом всё проходит встроенное сжатие: убираются ANSI-коды, от прогресс-баров остаётся последний кадр, повторы строк схлопываются, длинные строки обрезаются, а при выводе длиннее 300 строк остаются первые 150 и последние 100. Вывод меньше 1 КБ не трогается. Модели дописывается строка, на сколько сжато, и что полный вывод даёт `raw=true`.

Автоопределение rtk (`rtk pipe` без фильтра) и фильтры `log`/`git-log` не используются: на syslog автоопределение принимает строки за вывод grep, `log` выбрасывает строки без ERROR/WARN, а `git-log` оставляет один коммит. Команды rtk, которые сами запускают программу (`rtk git status`, `rtk systemctl`), здесь не работают: команды выполняются на удалённом сервере, а на серверах rtk не ставим. Статистика по дням, способам и последним командам — на странице «Экономия токенов». Без бинарника (`RTK_BIN` или `rtk` в PATH) работает только встроенное сжатие.

Обновление rtk устроено как у opencode. Раз в 6 часов плагин проверяет последний релиз на GitHub (`GET /api/plugins/rtk/version`). Если вышла новая версия, в углу появляется карточка «Обновить». `POST /upgrade` скачивает `rtk-oss` для своей архитектуры и сверяет sha256 из `digest` ассета GitHub. Затем он проверяет, что бинарник сообщает ожидаемую версию, и атомарно кладёт его в `/data/plugins/rtk/bin/rtk`. Перезапуск не нужен: rtk запускается на каждую команду. Из установленного и образного бинарника берётся тот, что новее. Поэтому после пересборки образа с более свежим rtk старая копия в `/data` не мешает. Если задан `RTK_BIN`, обновления отключены.

## Маскировка секретов (`plugins/secrets`)

Через `maskOutput` заменяет на `***` значения, которые модели видеть не нужно. Это присваивания с ключами `*password`, `*secret`, `*token`, `*api_key`, `PrivateKey` и подобными в форматах env, ini, yaml, json и `--flag=`. Ещё тело PEM-ключей (даже обрезанных), пароли в URL (`user:pass@`), `Authorization: Bearer/Basic`, хеши из `/etc/shadow` и токены с известными префиксами (GitHub, GitLab, Slack, AWS, Google, `sk-…`, JWT). `PasswordAuthentication`, `PWD` и `max_tokens` не трогаются. Модели дописывается, сколько значений скрыто. В аудит пишется только число (`secrets_masked`), сами значения не пишутся. Это список шаблонов, а не полноценный сканер: пароль в произвольном тексте он не узнает.

## Планировщик (`plugins/scheduler`)

Правый клик по серверу → «Запланировать задачу…»: агент, модель, задание, расписание (однократно, каждый день, по дням недели, раз в месяц), автопилот на время запуска. Время считается в часовом поясе браузера администратора, с учётом перехода на летнее время. Сторож раз в 30 с запускает задания, у которых подошло время. Запуск пропускается, если предыдущая задача этого задания ещё работает, и если SysAiAdm Station был выключен больше часа после назначенного времени (чтобы не стрелять ночное задание днём). История запусков — на странице «Планировщик».

## Терминал (`plugins/terminal`)

Значок терминала в правой панели сервера открывает SSH-сессию по WebSocket (`/api/plugins/terminal/ws/<nodeId>`). Маршрут, креды и пиннинг ключей те же, что у агента. Это инструмент администратора: фильтр опасных команд не действует, в аудит пишутся открытие и закрытие сессии. Cookie SameSite=Strict и проверка Origin не дают открыть терминал с чужого сайта. Не больше 8 сессий одновременно.

## WireGuard (`plugins/wireguard`)

Только клиент: контейнер SysAiAdm Station подключается к VPN-серверам площадок. У каждого `[Peer]` обязателен `Endpoint`, `ListenPort` запрещён — входящих подключений плагин не принимает.

Туннели хранятся в таблице `wg_tunnels`, конфиг зашифрован. Файл `<id>.conf` (0600) пишется в `/data/plugins/wireguard` только на время вызова `up`: обёртка копирует его в `/run/sysadm-wg/<id>.conf` (root, 0600) и поднимает `wg-quick` с копии. Root-обёртка `plugins/wireguard/sysadm-wg` (в образе `/usr/local/sbin/sysadm-wg`, sudo только на неё) принимает имя туннеля, а не путь, и повторно проверяет конфиг: разрешены только ключи Interface/Peer без PostUp/PreUp и DNS; `down` удаляет только интерфейсы WireGuard. Полный туннель (`0.0.0.0/0`) запрещён, если нет `Table = off`.

Автозапуск: при старте туннели с autostart помечаются «нужен поднятым»; сторож раз в минуту поднимает каждый такой упавший туннель. «Отключить» снимает пометку. Контейнеру нужен `cap_add: NET_ADMIN` и модуль `wireguard` в ядре хоста (`modprobe wireguard`, в ядрах ≥ 5.6 он встроен).
